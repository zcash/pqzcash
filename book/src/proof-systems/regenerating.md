# Regenerating the study's numbers

Every number on the PCS frontier page and in the two notes comes from one of three places: a
constant in [`pareto-model.py`](../../../ragu-pcs/pareto-model.py) typed from a paper or a
specification; a constant computed by a script in [`scripts/`](../../../ragu-pcs/scripts/) from an
external checkout; or the model's own arithmetic. This file says how to redo the first two kinds.
Paths are relative to [`ragu-pcs/`](../../../ragu-pcs/).

## The page's figures and claims

`python pareto-model.py` writes `pareto.html`, the standalone page, and the same page for the book
in four files that the book's chapter includes and serves: `pareto-book.html` (the text),
`pareto.css` (scoped to the page and coloured from mdbook's theme, with the plot and controls kept
dark), `pareto.js` and `pareto-data.js`. Every figure that the text quotes sits between markers in
[`pareto-template.html`](../../../ragu-pcs/pareto-template.html), in the two notes,
[`pasta-proof-size.md`](../../../ragu-pcs/pasta-proof-size.md) and
[`zk-fiat-shamir-with-aborts.md`](../../../ragu-pcs/zk-fiat-shamir-with-aborts.md), and in the
hardware wallets page, [`hardware-wallets.md`](../../../ragu-pcs/hardware-wallets.md), as
`<!--fig:NAME-->value<!--/fig-->`, and the model fills them when it writes the page. A qualitative
statement that the model can check is a named `claim(name, text, holds)` in `define_figures()`, and
the sentence it guards sits between `<!--claim:NAME:HASH-->` and `<!--/claim-->`, the hash the first
six hex digits of SHA-256 over the claim's text; a sentence that carries several claims names them
with commas. The run fails, and so does the book build, which runs the model, when any of these
holds:

- a figure's value in a tracked file differs from the model's;
- a claim no longer holds;
- a claim's hash in a marker differs from its text's, which means the claim was reworded and the
  sentence must be read again;
- a claim has no marker in any file, or a marker names no claim.

Commands:

```
python pareto-model.py            # write pareto.html; fail on a stale figure or marker, or a failed claim
python pareto-model.py --fill     # also write the current values and hashes back into the tracked files
python pareto-model.py --figures  # list every figure and every claim
```

A new number in the text gets a `fig()` in `define_figures()` and a marker where it is quoted; a
qualitative statement that the model can check gets a `claim()` and a marker around its sentence.
`--fill` prints each changed figure as old → new and each changed claim with its new text, which is
the list of sentences to read before committing. A constant that a script computes goes in the model
with a comment naming the script and its inputs, as `RANK_SUMS_147`, `WIDTH_SHRINK_147` and
`WHIR_147` do.

## Akita

- **Openings, slopes, rows and the catalog report** (`AKITA_128`, `SLOPE[128]`, `ROWS`,
  [`estimates/`](../../../ragu-pcs/estimates/)):
  [`scripts/akita-pasta-estimates.sh`](../../../ragu-pcs/scripts/akita-pasta-estimates.sh) builds
  the patched Akita and runs the rank ladder
  ([`pasta-rank.csv`](../../../ragu-pcs/estimates/pasta-rank.csv)), the catalog re-pricing, the
  re-plans under each pricing override, and the 128-bit width tables for Pallas and Goldilocks. It
  writes the TSVs and CSVs that [`estimates/`](../../../ragu-pcs/estimates/) holds. The catalog
  security report there is `gen_schedule_artifacts --catalog-report` over the shipped families,
  built with the `catalog-security` feature, as the re-plan scripts run it. The per-K group runs
  behind the opening tables are not kept under [`estimates/`](../../../ragu-pcs/estimates/); the
  re-plan scripts reproduce them.
- **The 165-bit level's plan** (`AKITA_165_PLANNED`, `SLOPE[165]`,
  `LEVEL3_COMPRESSION_CELLS`, `RANK_SUMS_165`):
  [`scripts/akita-165-pipeline.sh`](../../../ragu-pcs/scripts/akita-165-pipeline.sh), on the
  `level3-165` worktree, regenerates the width tables at 165 bits (about four hours;
  `SKIP_TABLES=1` resumes), re-sizes the nine compression cells and checks that each covers its
  map, rebuilds, and runs the re-plan into `work/akita-165-out/replan`. Then:

  ```
  python scripts/akita-150-page-inputs.py work/akita-165-out/replan
  python scripts/linf-accumulation-widths.py 165 \
      work/akita-src-165/crates/akita-params/src/sis/generated_sis_table - - \
      > estimates/linf-accumulation-widths-165.tsv
  python scripts/derive-linf-widths.py 147 165 estimates/linf-accumulation-widths.tsv pallas \
      > estimates/linf-accumulation-widths-derived.tsv
  python scripts/rank-scale.py estimates/catalog-security.tsv \
      work/akita-src/crates/akita-params/src/sis/generated_sis_table \
      work/akita-src-165/crates/akita-params/src/sis/generated_sis_table \
      estimates/linf-width-table-goldilocks.csv estimates/linf-width-table-goldilocks.csv
  ```

  The first prints the opening's bytes; its slopes are from 2^14 to 2^16, and the model's are from
  the 2^14 and 2^24 rows of the same files (2^26 for Goldilocks). The second writes the level's
  accumulation widths for the 64-bit and 128-bit moduli, and the third derives Pallas's, which the
  estimator has not been run for at the level. Deriving all three moduli and running
  `scripts/derive-linf-widths.py --check DERIVED.tsv estimates/linf-accumulation-widths-165.tsv`
  gives the rule's error against the estimator: a median of +0.004 in log2 of the width for the
  64-bit modulus and +0.014 for the 128-bit one, with 5th to 95th percentiles of about -0.12 to
  +0.48. The last command's `own` line is the level's module-rank growth for the catalog's own
  moduli; its `q64` line is not meaningful there, since the 64-bit modulus's CSV table at the level
  has not been generated and the 128-bit one stands in for it.
- **The 147-bit floor** (`AKITA_147`, `SLOPE[147]`):
  [`scripts/akita-147-pipeline.sh`](../../../ragu-pcs/scripts/akita-147-pipeline.sh), on the
  worktree that the checkout script made, regenerates its width tables at 147 bits (hours;
  `SKIP_TABLES=1` resumes), re-sizes the compression cells, rebuilds and runs
  [`scripts/akita-147-replan.sh`](../../../ragu-pcs/scripts/akita-147-replan.sh); then `python
  scripts/akita-150-page-inputs.py work/akita-147-out/replan` prints the two dicts in the model's
  shape. [`scripts/akita-150-tables.sh`](../../../ragu-pcs/scripts/akita-150-tables.sh) writes CSV
  width tables at a given floor for every modulus, and the Pallas table alone is
  `infinity_width_table --policy Quantum147BitADPS16 --profiles pallas --format csv --profile
  local-minimum --output ...` in the worktree: 5.5 hours with the estimator built without its
  `parallel` feature.
- **The 165-bit level's derived parts** (floor key 165): the Pallas modulus's accumulation-width
  table is extrapolated from the 147-bit rows by
  [`scripts/derive-linf-widths.py`](../../../ragu-pcs/scripts/derive-linf-widths.py), whose
  `--check` tests the rule on the estimator's own tables; the compression chain's security
  (`LEVEL3_COMPRESSION_CHAIN`, `SHIPPED_COMPRESSION_CHAIN`) is printed by
  [`scripts/compression-chain.sh`](../../../ragu-pcs/scripts/compression-chain.sh) from Akita's
  single-instance estimator, in a checkout with the estimator's examples built.
- **Module-rank growth** (`RANK_SUMS_147`): over the weakest instance of each of the catalog
  report's 115 schedules, the least module rank that covers its width at each floor, mapped through
  each variant's modulus:

  ```
  python scripts/rank-scale.py estimates/catalog-security.tsv \
      work/akita-src/crates/akita-params/src/sis/generated_sis_table \
      work/akita-src-150/crates/akita-params/src/sis/generated_sis_table \
      estimates/linf-width-table-goldilocks.csv work/akita-147-out/linf-width-table-147-goldilocks.csv \
      estimates/linf-width-table-pallas.csv work/akita-147-out/linf-width-table-147-pallas.csv
  ```

- **Width shrink** (`WIDTH_SHRINK_147`): the median of the 128-bit width over the 147-bit one, per
  modulus and ring dimension, over the cells where neither width is at the estimator's search cap
  and the width falls. The shipped moduli come from the production table's policy audit at each
  floor, Pallas and Goldilocks from the CSV tables:

  ```
  python scripts/width-shrink.py 147 \
      work/akita-src/crates/akita-params/src/sis/generated_sis_table/policy_audit.csv \
      work/akita-src-150/crates/akita-params/src/sis/generated_sis_table/policy_audit.csv \
      pallas=estimates/linf-width-table-pallas.csv:work/akita-147-out/linf-width-table-147-pallas.csv \
      goldilocks=estimates/linf-width-table-goldilocks.csv:work/akita-147-out/linf-width-table-147-goldilocks.csv
  ```

- **The accumulation matrix** (`LINF_WIDTHS`,
  [`estimates/linf-accumulation-widths.tsv`](../../../ragu-pcs/estimates/linf-accumulation-widths.tsv)):
  the largest width that Akita's ℓ∞ estimator certifies at each module rank and each bound of the
  catalog's ladder, at ring degrees 512 and 1024, for the Pallas, 64-bit and 128-bit moduli at both
  floors. The 64-bit and 128-bit moduli come from the production tables the estimator writes into
  `akita-params` (`generated_sis_table/q64.rs`, `q128.rs`, in the pinned checkout at 128 bits and
  the 147-bit worktree at 147), Pallas from the CSV width tables above; the Goldilocks CSV tables
  are checked to coincide with the 64-bit modulus's rows, which the Goldilocks variant reads. The
  estimator evaluates only the catalog's own cells, so a bound is rounded up to the ladder:

  ```
  python scripts/linf-accumulation-widths.py \
      128 work/akita-src/crates/akita-params/src/sis/generated_sis_table \
          estimates/linf-width-table-pallas.csv estimates/linf-width-table-goldilocks.csv \
      147 work/akita-src-150/crates/akita-params/src/sis/generated_sis_table \
          work/akita-147-out/linf-width-table-147-pallas.csv work/akita-147-out/linf-width-table-147-goldilocks.csv \
      > estimates/linf-accumulation-widths.tsv
  ```

- **The hiding padding's hardness** (`HIDING_PADDING_ATTACK_BITS`, `HIDING_PADDING_SWEEP`): the
  pinned lattice estimator in Akita's `third_party` submodule, which the checkout script
  initialises, under Sage, costs every LWE attack on the knapsack-LWE instance behind the hardware
  wallet's padding at 5,000 bits and 1,024, 1,385, and 2,048 rows, then sweeps the padding from
  3,500 to 6,000 bits at the device's 1,024 rows, by 250 and by 50 where the floors are crossed,
  under the ADPS16 quantum model: `sage scripts/knapsack-lwe-check.py` from `ragu-pcs`, about an
  hour.

- **Typed from the paper and the notes**: the verifier times (`AKITA_VERIFY_MS`, Table 16), the
  terminal's inner-image coordinates (`IMAGE_COORDS`, pasta-proof-size.md §6.1), and the mask's
  parameters (`MASK_*`, the zero-knowledge note's §5).

## WHIR, FRI and the limb hybrid

- **The sweeps** ([`estimates/whir-sweep.tsv`](../../../ragu-pcs/estimates/whir-sweep.tsv),
  [`estimates/whir-sweep-grind.tsv`](../../../ragu-pcs/estimates/whir-sweep-grind.tsv)): the
  reference binary at 2^17, 2^18 and 2^20 variables over `Field256` and `Goldilocks3`, rates 1/2 to
  1/64, maximum proof of work 0, 16, 20 and 24 bits, 128 bits in the Johnson regime, three verifier
  repetitions:

  ```
  target/release/main -l 128 -d 17 -r 3 -f Field256 -p 20 --reps 3
  ```

Each run prints `Proof size`, `Average hashes` and `Prover time`, which are the TSV's `proof_KiB`,
`verifier_khashes` and `prover_ms`; `first_samples` and `queries` are the first round's sample count
and the sum over rounds from its `commit ... samples N` lines.
- **The quadratic extension under BEEP**
  ([`estimates/whir-sweep-beep.tsv`](../../../ragu-pcs/estimates/whir-sweep-beep.tsv)): with the
  patch under `scripts/patches/whir/` applied by `git am` and the build repeated,
  [`scripts/whir-sweep-beep.sh`](../../../ragu-pcs/scripts/whir-sweep-beep.sh) runs the same grid
  over `Goldilocks2` and prints the table. The patch is a diagnostic, not a sound configuration: it
  takes the fold's error as BEEP's, and BEEP's samples are not sent. It quotes lines of the
  reference implementation, which is MIT or Apache-2.0. The table's sizes and counts are
  deterministic; its prover times are not used.
- **The higher floor** (`WHIR_147`):
  [`scripts/whir-sweep-147.sh`](../../../ragu-pcs/scripts/whir-sweep-147.sh) runs the same binary at
  128 and 147 bits over both fields at rates 1/2 to 1/8; the model takes the mean ratios.
- **Zero knowledge** (`ZK_BYTES`, `ZK_HASHES`, `ZK_PROVER`): Plonky3's HVZK-WHIR benchmark,
  `RUSTFLAGS="-Ctarget-cpu=native" cargo bench --bench zk_overhead -p p3-whir -- whir_zk_overhead`
  in `work/plonky3-src`.
- **FRI's factors** over WHIR (1.95 on the proof, 2.07 on the hashes) are the WHIR paper's
  measurements, typed.

## BitZ

`BITZ_MEASURED` is the proof of concept's own benchmark on one thread, by
[`scripts/bitz-st-sweep.sh`](../../../ragu-pcs/scripts/bitz-st-sweep.sh), after
`scripts/bitz-rerun.sh build`:

- `scripts/bitz-st-sweep.sh st 22-29 udrg:1:4:128 udrg:3:4:128` for the unique-decoding rows, rates
  1/2 and 1/8 at 128 bits; and
- with the patch under `scripts/patches/bitz/` applied by `git am` and the build repeated,
  `scripts/bitz-st-sweep.sh st 22-28 beep:custom:1:4:128` and so on to `beep:custom:6:4:128`, for
  the rows derived from BEEP, rates 1/2 to 1/64.

Then `python scripts/bitz-summary.py work/bitz-out/st/sweep-*.log` gives the table of commit,
grand-product, Ligerito and verifier times and proof bytes. `BITZ_QUERIES` are the per-level query
counts of each run's resolved configuration, which its `RESULT` line carries hex-encoded.

The script sets `RAYON_NUM_THREADS=1`. The benchmark's `--threads 1` sizes only its main thread
pool, and the library's Merkle trees, encoder, combine step and lincheck fold hop onto a second
pool of every core unless that variable is set. The script also refuses to start on battery power
where it can tell. [`scripts/bitz-pcs-sweep.sh`](../../../ragu-pcs/scripts/bitz-pcs-sweep.sh) and
[`scripts/bitz-overnight.sh`](../../../ragu-pcs/scripts/bitz-overnight.sh) are earlier sweeps of
the same benchmark that do not set the variable; their times are not used.

The patch is a diagnostic, not a sound configuration: it lets the Johnson profile run at a 128-bit
target by dropping three checks, which the model's comment on `BITZ_MEASURED` lists. It quotes
lines of the proof of concept, which is MIT-licensed, and of its vendored flock-mod, which is MIT
or Apache-2.0.
